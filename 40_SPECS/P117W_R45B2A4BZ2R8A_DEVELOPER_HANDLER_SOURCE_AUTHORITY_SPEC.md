## Purpose

The EFSM designer is developer tooling. A GUARD or ACTION created by a developer must correspond to real PHP code, not merely to a string invented in `fsm.json`.

R7 already binds transition guards/actions only to handlers actually registered by the application. R8A adds the missing source authority and mutation pipeline so application handlers can be genuinely developer-programmed through OWASYS in the next graphical slice.

R8A deliberately does not yet enable the GUARD/ACTION Create/Edit toolbar buttons. It establishes and verifies the executable-source foundation first; R8B consumes it from the graphical designer.

## EFSM semantics retained

- STATE remains a state identity/relationship object; no module/route/template authoring is reintroduced by this slice.
- SIGNAL remains the transition input; OWASYS signals may originate from user or automate.
- GUARD is developer-programmed PHP evaluated by the EFSM processor; dynamic `acl:<resource>:<action>` guards remain generated by the application security adapter and their `acl:` namespace is reserved.
- ACTION is developer-programmed PHP registered into `FsmActionDispatcher`.
- `push`, `pop`, `poke`, `peek` remain EFSM runtime primitives and are not developer ACTION handlers.
- no alternate control engine or second FSM model is introduced.

## Generic OPUS evolution

Add:

- `Opus/Fsm/Definition/FsmHandlerSourceEditorInterface.php`
- `Opus/Fsm/Definition/FsmHandlerSourceEditor.php`

The concrete editor implements the homonymous interface. That interface extends directly the four mandatory OPUS framework interfaces.

The generic editor:

- operates on explicit managed guard/action regions in a PHP source file;
- supports `create` and `update` of one named callable;
- never calls `eval`;
- rejects PHP open/close tags, NUL, managed-marker injection and invalid handler IDs;
- bounds one handler body to 16384 bytes;
- requires an anonymous PHP function expression (`function (...)` or `static function (...)`);
- validates the complete candidate source with PHP native token parsing (`token_get_all(..., TOKEN_PARSE)`);
- reparses the managed region after mutation and verifies the handler SHA-256 before returning the candidate;
- never persists files itself.

Persistence remains delegated to the existing generic `SiteSourceWorkspace`, which provides optimistic locking, bounded source mutation, atomic write and Profiler instrumentation.

Executable authority remains the actual runtime registration maps. JSON descriptions remain metadata only. A managed handler that is not actually registered is rejected.

## Secured authoring flow

The mutation path is strictly:

`owasys-front -> secured REST -> owasys-back -> allow-listed Composer provider -> generic SiteSourceWorkspace -> response -> owasys-front`

Add REST resource:

`PUT /api/v1/applications/{site_id}/fsm/handlers`

Operation:

`fsm.handler.write`

Composer alias:

`owasys:fsm-handler-write -> owasys:fsm:handler-write`

Allowed roles: `admin`, `developer`. Backend ACL remains deny-by-default and its existing `fsm:*` developer capability covers the operation.

The backend receives only bounded structured fields: site id, guard/action kind, handler id, create/update mode, expected managed-source SHA-256 and handler PHP source. It revalidates all fields, reserves `acl:` for dynamic security guards, applies the generic managed-source editor, then persists through `SiteSourceWorkspace` with optimistic locking.

No JavaScript, TypeScript, Node.js or JavaScript package dependency is added to `sites/owasys-back`.

## CSRF cause corrected before graphical authoring

The current R7 designer loads the read-only handler catalog with the same single-use CSRF token later used for a mutation. The gateway currently consumes that token while serving the catalog, so the first subsequent semantic mutation can reuse a dead token.

R8A corrects the cause:

- read-only handler-catalog retrieval does not consume the CSRF token;
- draft/handler mutations consume it;
- every JSON success/error response issues/returns the current/new designer token;
- frontend designer JavaScript adopts the returned token before the next request.

This makes repeated designer mutations compatible with the existing single-use CSRF manager.
