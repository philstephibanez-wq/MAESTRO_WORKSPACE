## Context

The OWASYS Applications screen currently renders every registry entry as a peer branch below one OWASYS root. This is misleading because OWASYS is contractually composed of exactly two autonomous OPUS applications: `owasys-front` and `owasys-back`. Applications created by OWASYS, such as `essai`, are managed/generated applications and are not a third internal OWASYS component.

## Authoritative source finding

The current SCORE template `sites/owasys-front/application/registry/templates/index.score` iterates the single `entries` collection below the OWASYS root, which visually flattens system components and generated applications into the same tree level.

`OwasysRuntimeController::registryViewData()` already exposes `entry.deletable` only when the registry entry is generated by Composer, has role `generated-opus-application`, and is not `owasys-front` or `owasys-back`. The existing data therefore already contains enough presentation information for the current registry contract; no REST, backend, registry storage or business-model mutation is required.

## Required presentation

The Applications tree must read visually as:

- one OWASYS parent card;
- inside the OWASYS parent card, the two protected/system application cards `owasys-front` and `owasys-back`;
- outside the OWASYS internal card, a distinct applications area containing generated applications such as `essai`;
- generated applications retain their current selection, current-state, Singleton, metadata and deletion controls;
- no generated application is presented as a third internal OWASYS component.

No application ID is to be hardcoded for generated applications. The existing generated/deletable registry projection drives their placement.

## Scope

Bounded OWASYS front/SCORE presentation change only:

- `sites/owasys-front/application/registry/templates/index.score`

No PHP, REST catalog, backend, registry schema, FSM, ACL, SSO, Composer command, source browser or OPUS framework file is changed.

## I18n

No new literal UI text or locale key is introduced. The layout reuses the existing translated keys and current entry metadata/status badges, so all existing locales keep their normal fallback behavior unchanged.
